# Push i18n Plan 22: French push notifications Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Push notifications arrive in the language the user chose in the app (French or English), per device, with no rules, indexes or schema migration.

**Architecture:** The app's language is a per-DEVICE choice (Settings, persisted in `shared_preferences`; "System default" follows the device). Push tokens are per device too, so the language is stored ON THE TOKEN DOCUMENT: `users/{uid}/fcmTokens/{token}` gains a `lang` field (`'en'` | `'fr'`). Cloud Functions build the payload per recipient language: `sendToUser` groups the user's token docs by `lang` and sends one multicast per language. Token docs without `lang` (written by app versions before this change) are English, which is exactly today's behaviour, so the client and the Functions can be released in either order. The existing `fcmTokens` rule (`allow read, write: if isOwner(uid)`) already allows the new field: NO change to `firestore.rules` or indexes.

**Tech Stack:** TypeScript Cloud Functions (`firebase/functions`, jest), Flutter client (`lib/features/notifications`, `lib/core/locale`), Riverpod 3.

## Global Constraints

No firebase deploy of any kind (the CD pipeline deploys Functions after merge to `develop`; that is the owner's pipeline).
- English push text is BYTE-IDENTICAL to today's for every notification (existing `firebase/functions/test/payloads.test.ts` assertions stay and must pass unchanged). The data payload keys and values (`type`, `mealId`, `matchId`, `status`, `reminder`, `reopened`) are language-independent and unchanged: the app's tap routing (`push_route_mapper.dart`) must keep working.
- Supported push languages: `en`, `fr`. Anything else (missing, unknown, `fr-CA`, etc.) normalises to `en` for stored values; the client only ever writes `en` or `fr`.
- French copy: informal "tu", short and warm, same meaning as the English, typographic apostrophe `’`, non-breaking space U+00A0 before `: ! ? ;` and inside « » (push text is plain text, the NBSP characters are written as ` ` escapes in the TS source so they are visible), brand "Convyve" untranslated; terminology as in `docs/l10n/FRENCH-REVIEW.md` (tabs "Messages"/"Demandes", "Hôte", "Convive"; no gendered forms: avoid "invité(e)" style; prefer neutral wording like "Quelqu’un veut se joindre à ton repas"). Paris times stay `Europe/Paris`, 24-hour (`20:00`).
- Privacy: `lang` is not personal data beyond what the app already stores (the token doc already has `platform`); nothing else is added. Do not log token values or message text.
- Do NOT run `dart format` on directories or files you do not otherwise edit; `git status` shows only intended files before every commit; never commit `.superpowers/`, `graphify-out/`, `ux_audit/out/`. Commit trailer: the `Co-Authored-By:` line the harness specifies at that time.

### Task 1: Functions: language-aware payloads and per-language sends

**Files:**
- Modify: `firebase/functions/src/lib/payloads.ts`, `firebase/functions/src/lib/reminders.ts` (day label helper only if needed), `firebase/functions/src/lib/messaging.ts`, and every caller: `triggers/request_created.ts`, `triggers/request_updated.ts`, `triggers/message_created.ts`, `scheduled/meal_reminder.ts`, `scheduled/post_meal_reminder.ts`, `callable/delete_account.ts`, `callable/cancel_matched_meal.ts`
- Create: `firebase/functions/src/lib/push_lang.ts` (the `PushLang` type, `normalizePushLang`, `groupTokensByLang`)
- Tests: `firebase/functions/test/payloads.test.ts` (extend, keep existing assertions), `firebase/functions/test/push_lang.test.ts` (new), `firebase/functions/test/reminders.test.ts` (extend only if reminders.ts changes)

**Interfaces:**
- `type PushLang = 'en' | 'fr'`; `normalizePushLang(v: unknown): PushLang` returns `'fr'` only for the exact string `'fr'`, else `'en'`.
- Every `build*` function in `payloads.ts` gains a trailing parameter `lang: PushLang = 'en'` (existing call shapes and defaults unchanged; `buildMealReminder(kind, restaurantName, mealAt, now, mealId = '', lang = 'en')`, `buildMatchLeft(reopened, mealId = '', withdrew = false, lang = 'en')`, `buildMealCancelled(mealId = '', byHost = false, lang = 'en')`, etc.). Copy lives in one table keyed by language so French strings can be reviewed in one place; `data` is language-independent.
- Reminder titles: English unchanged ("Your meal is today/tomorrow", "Your meal is coming up"); French e.g. "Ton repas, c’est aujourd’hui" / "Ton repas, c’est demain" / "Ton repas approche": the day word comes from a language table (`today`/`tomorrow` -> `aujourd’hui`/`demain`), not from string-replacing English. Body: English "<restaurant> at 20:00" unchanged; French "<restaurant> à 20:00" (24-hour `HH:mm`, no NBSP needed).
- `groupTokensByLang(docs: { id: string; data(): Record<string, unknown> }[]): Map<PushLang, string[]>` (pure, unit-tested): token ids grouped by `normalizePushLang(doc.data().lang)`.
- `sendToUser(databaseId, uid, payload: PushPayload | ((lang: PushLang) => PushPayload))`: a plain `PushPayload` keeps working for any caller that does not care (sends as before, all tokens together). With a function, read the token docs once, group by lang, call the function once per language present, `sendEachForMulticast` per group, and prune invalid tokens across all groups exactly as today (`tokensToPrune`). All eight call sites pass the function form `(lang) => buildX(..., lang)`.
- Behavioural guarantees: a user with zero tokens sends nothing (as today); one failing language group never prevents the other group from sending (each group's send is wrapped so a thrown error in one does not skip the other, but errors are still surfaced the way today's single send surfaces them: do not swallow silently: log the error code only, never tokens/text, then rethrow after all groups were attempted if any group threw).

- [ ] **Step 1: Tests first (red):** `payloads.test.ts`: existing three tests unchanged and green; for EVERY builder an English-default test pinning the exact strings (copy them from the current source so English is provably unchanged) and a French test asserting the French title/body (including a name with an apostrophe, a long restaurant name truncated at 80, a 500-char message truncated at 120, the NBSP escapes before `?`/`!` where the copy has them); `data` identical across languages for every builder. `push_lang.test.ts`: `normalizePushLang` (`'fr'`, `'en'`, `undefined`, `null`, `'FR'`, `'fr-FR'`, `42` -> en except exact `'fr'`); `groupTokensByLang` (mixed, missing `lang`, all fr, empty); `sendToUser` function form with a faked `getFirestore`/`getMessaging` seam: extract the send into a function that takes the db reader and the messaging sender as parameters (`sendToUserWith(deps, ...)`) so jest can assert one multicast per language with the right payload, pruning across groups, nothing sent for zero tokens, and that a throwing group does not stop the other.
- [ ] **Step 2: Implement; update the eight call sites; Step 3: gates** (`npm run build`, `npm run lint`, `npm test` from `firebase/functions`); commit `feat(functions): push notifications in the device's language (en/fr) from the token doc's lang`.

### Task 2: App: write the language on the token document

**Files:**
- Modify: `lib/core/locale/locale_controller.dart` (add the pure resolver), `lib/features/notifications/domain/repositories/push_repository.dart`, `lib/features/notifications/data/repositories/push_repository_impl.dart`, `lib/features/notifications/application/push_registration_controller.dart` (+ providers), `docs` mentions found by grep
- Tests: `test/core/locale/`, `test/features/notifications/` (data repository test + controller test)

**Interfaces:**
- `String resolveAppLanguage(Locale? choice, List<Locale> deviceLocales)` (pure, in `lib/core/locale/`): returns `choice.languageCode` when `choice` is non-null and supported (`en`/`fr`), else the language code of the FIRST device locale whose language code is supported, else `'en'`. Must agree with what the UI shows: `MaterialApp`'s default resolution for `[en, fr]` (first matching device language wins; no match -> `en`): add a test that proves agreement for representative device lists (`[fr_FR]`, `[fr_CA]`, `[es, fr]`, `[de]`, `[]`, `[en_US, fr]`).
- `PushRepository.registerToken(String uid, {required String lang})` and a new `Future<void> updateTokenLanguage(String uid, String lang)`: writes `lang` to the current token doc with `set(..., SetOptions(merge: true))` (never overwriting other fields; if the doc does not exist yet it is created by the next `registerToken`, so `updateTokenLanguage` with no token does nothing). The token-refresh subscription writes the token doc with the CURRENT language too: keep the language in a field of the repository (`_lang`) updated by `registerToken`/`updateTokenLanguage` so a refresh that happens after a language change writes the new one. Language is always normalised to `en`/`fr` before writing.
- `PushRegistrationController`: when it registers (sign-in / permission granted flow, see the file), pass `lang: resolveAppLanguage(ref.read(localeControllerProvider), PlatformDispatcher.instance.locales)`. Then `ref.listen(localeControllerProvider, ...)` while a user is registered: on a change call `updateTokenLanguage(uid, resolved)` (best-effort in try/catch: failure must not reach `PlatformDispatcher.onError`; log the type only). Also refresh the stored language on each cold start register (registerToken runs on every sign-in/app start already; confirm). Follow the sign-out rule from plan 17b: read the repository and uid BEFORE any await; do not touch the controller after dispose.
- Device-language changes while "System default" is selected: the OS language changes outside the app; the next app start re-registers with the new device language (accepted; note in docs). No new background listeners.

- [ ] **Step 1: Tests first (red):** resolver table tests (including agreement with Flutter's default resolution via `basicLocaleListResolution(deviceLocales, supportedAppLocales)` as the oracle); repository tests with the existing fake Firestore: `registerToken(uid, lang: 'fr')` writes `lang: 'fr'` plus the old fields; unknown lang normalises to `en`; `updateTokenLanguage` merges only `lang` (other fields intact, `updatedAt` untouched or refreshed: pick and assert), does nothing without a token; the refresh stream writes the CURRENT language after `updateTokenLanguage`; controller tests: registers with the resolved language, a locale change triggers one `updateTokenLanguage`, signed-out/unregistered locale change does nothing, a failing write does not throw out.
- [ ] **Step 2: Implement; Step 3: gates** (`fvm flutter analyze`, `fvm flutter test`); commit `feat(notifications): store the app language on the push token so the server can localize pushes`.
