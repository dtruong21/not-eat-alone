# UX Pass Part B, Plan 19: French + English (tu) and an In-App Language Switch

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the app in French and English for the Paris launch: every user-facing string comes from ARB files (English source, French draft in the informal "tu"), dates and times follow the language through `intl`, the app follows the device language by default, and Settings has a Language row (System default / English / Français) whose choice is remembered.

**Architecture:** Flutter `gen_l10n` with `lib/l10n/app_en.arb` (source) and `app_fr.arb`, generated classes COMMITTED under `lib/l10n/generated/` (CI runs `build_runner` only, not `gen-l10n`). A tiny `context.l10n` extension falls back to English when a widget tree has no localisation delegates, so the ~900 existing widget tests (which pump a bare `MaterialApp` and assert English text) keep passing unchanged; new French tests use a `pumpLocalized` helper. A `LocaleController` (Riverpod notifier, `shared_preferences`) holds `Locale?` (null = follow the device), seeded synchronously at bootstrap so there is no language flash. `core/util/date_format.dart` keeps its function names but renders through `intl` `DateFormat` for the active locale. Analytics event names/params, error codes and exception messages stay English; server-sent push text is out of scope (follow-up).

**Tech Stack:** Flutter via FVM (`fvm flutter ...`), `flutter_localizations` (SDK), `intl` (the version `flutter_localizations` pins), `shared_preferences`, Riverpod, `flutter_test` + `mocktail`.

Spec: `docs/superpowers/specs/2026-10-05-ux-pass-design.md` (§6: French + English, informal "tu", language switch in Settings). Owner answers (2026-10-12): persistence via `shared_preferences` (also usable to persist the Paris-notice dismissal: do that in Task 1 as a small bonus if trivial, else follow-up); French is drafted by me and reviewed by a native speaker before store submission (Task 8 produces the review table). Cost estimate and string inventory: `docs/ux/AUDIT.md` X-13.

IMPORTANT, develop keeps moving (another session adds UI and strings): before each task `git fetch` and merge/rebase this branch onto `origin/develop` if it moved; extract strings in the files as they are NOW, not from the audit's line numbers. Any English string added on `develop` after this plan lands will be un-extracted: Task 8 adds a guard test (a grep of `lib/features` and `lib/core` for hard-coded user-facing literals with an explicit allow-list) so regressions are visible.

## Global Constraints

- Flutter via FVM always. `fvm flutter analyze`: 0 errors AND 0 warnings (CI fails on warnings, e.g. `unused_element`, `unused_import`), no new lints in touched files. `fvm flutter test` green after every task.
- Dependency rule `presentation → application → domain ← data`; `AppLocalizations` is used ONLY in `presentation/` (widgets) and in `core/` UI helpers; domain/data never import it. Where a domain/application layer currently returns user-facing English (e.g. `inboxActionMessage`, error message mapping), return an enum/typed value and map it to a localized string in presentation: do not call `context` from application code.
- New dependencies allowed in this plan ONLY: `flutter_localizations` (sdk), `intl`, `shared_preferences`. Nothing else.
- ARB rules: keys camelCase with a feature prefix (`signinTitle`, `mealDetailRequestToJoin`); every key has an `@key` description; placeholders typed with `placeholders` metadata; counts use ICU `plural`; **ICU apostrophes: a literal `'` in a message must be written `''`** (French is full of them: `l''équipe`); prefer the typographic apostrophe `’` in French copy to avoid escaping; en and fr MUST have identical key sets and placeholders (a parity test enforces it).
- French: informal "tu" everywhere; short, warm, same tone as the English; keep brand/app name "Convyve"; "Women only" = "Entre femmes"; prices/units n/a; 24-hour clock, `lun. 5 oct.`-style dates from `intl`; "Today/Tomorrow/Yesterday" = "Aujourd’hui/Demain/Hier"; do not translate analytics or log text.
- Keys and widget `Key`s are unchanged; E2E (`integration_test/`) finds widgets by key, and runs in the test locale (English): `make e2e` must stay green without edits (if a finder uses English text it keeps working because the E2E app locale is English: but check `integration_test/` for text finders that depend on strings you changed).
- Strings that must NOT be translated: `Convyve` brand, `supportEmail`, URLs, analytics event/param names, debug/log prints, exception `toString`s, the "Language" picker's own option labels (`English`, `Français`: native names, same in both languages).
- Accessibility labels (Semantics, tooltips) are user-facing: extract them too.
- Layout: French is ~15-25 % longer: every extracted screen must still pass the existing 320 px / 2.0x no-overflow tests; Task 8 adds French variants for the longest strings.
- Tokens, `context.wp`, AppButton etc. as before; no new design tokens needed.
- Do NOT run `dart format` on directories or on files you do not otherwise edit; format only new files; check `git status` shows only intended files before every commit. Generated l10n files ARE committed (`lib/l10n/generated/`): regenerate with `fvm flutter gen-l10n` and commit the diff with the ARB change. Do not commit anything under `graphify-out/`, `.superpowers/`, `ux_audit/out/`. Commit trailer: the `Co-Authored-By:` line the harness specifies at that time.
- No `firestore.rules`, Cloud Functions or CI workflow changes. No firebase deploy.
- Capture runs use only the simulators `Convyve E2E` and `Convyve UX Small`, never the generic `iPhone 17 Pro`.

**Interfaces:**
- Each formatter gains a REQUIRED-with-default `Locale locale` (default `Locale('en')`) so existing tests still pass: `formatMealDateTime(value, {DateTime? now, Locale locale})`, `formatClockTime(value, {Locale locale})`, `formatMonthDay`, `formatLongDate`, `formatDayLabel`. "Today/Tomorrow/Yesterday" words come from a small private table keyed by language code (`en`, `fr`) in `date_format.dart` (NOT `AppLocalizations`: core util stays context-free; keep the ARB keys out of this task unless a callsite needs them). Everything else from `intl`: 24-hour `DateFormat.Hm(locale)`, weekday/day/month `DateFormat('EEE d MMM', locale)`, year variant `DateFormat('EEE d MMM y', locale)`, long date `DateFormat.yMMMMd`/`'d MMMM y'`. English output must stay byte-identical to today's (`Sat 10 Oct, 20:00`, `Today 20:30`, `5 Jan`, `5 January 2027`): the existing English tests are the regression suite. French examples: `sam. 10 oct., 20:00`, `Aujourd’hui 20:30`, `Demain 12:30`, `5 janv.`, `5 janvier 2027` (accept whatever `intl` produces for abbreviations and assert it literally in tests).
- Call sites pass `Localizations.localeOf(context)` (they are all in widgets).
