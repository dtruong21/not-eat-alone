## [P3] Minor findings from the second sweep (docs, reminders races, validation gaps, analytics, privacy hygiene)

Each item is independent; none blocks a release. Severity P3 unless noted.

**Closed bug found NOT fully fixed: `closed/2026-10-09-docs-contradict-code.md`** - stale statements remain: `docs/TEST-PLAN.md:336` still lists "Live account deletion via UI (requires Blaze plan; current callable requires manual backend trigger ...)" under *Deferred* although Settings -> Delete account ships; `docs/RELEASE.md:5` says "App Check ... enforcement is off" (true for the console products, not for the callables) while `deleteAccount`, `cancelMatchedMeal` and `searchRestaurants` set `enforceAppCheck: true` in code (a build without a valid attestation, e.g. a sideloaded release APK without Play Integrity or an unregistered debug token, cannot search restaurants, cancel or delete an account); `docs/RELEASE.md:85` "all 5 functions should be green" (the codebase exports 15) and the function names in 1.4 (`onRequestCreated` ...) differ from the deployed export names (`requestCreatedDefault` ...), which matters because `firebase deploy --non-interactive` refuses to delete functions that exist remotely but not in source unless `--force` is passed (NOT VERIFIED against the project); `docs/RELEASE.md:452,463` still say 215 tests.

**Scheduled functions are not transactional (`mealReminder`, `postMealReminder`):** the meal is read once, pushes are sent, then `doc.ref.set({flag:true},{merge:true})` is written from the stale snapshot. If the guest withdraws (or the host deletes the account) inside that window: the withdrawn guest still gets "Your meal is tomorrow", the flag is set on the *reopened* meal so its next match gets no reminder, and `set(..., merge)` on a just-deleted meal recreates a field-less stub `meals/{id}`. `postMealReminder` also sends to the host before the guest and writes the flag last, so a failure on the guest send repeats the host's "How was it?" push at the next hourly run. Use an `update` guarded by a transaction (status `matched` and same `guestId`) and `Promise.allSettled` like `mealReminder`.

**Loose validation outside meals/requests (rules emulator):** `profiles/{uid}` accepts `displayName: 12345`, a 200 KB `bio` and `photoUrls: 'not-a-list'` (one user can make their own profile unparseable for everyone who opens it, and `photoUrls` may point to any host, so viewers' devices fetch arbitrary URLs); `reads/{uid}` and `blocks` have no key whitelist. Skipped test: `client_write_shapes.rules.test.cjs` "profiles: displayName/bio/photoUrls are typed and size-capped". `onRatingCreated`'s `set(..., {merge:true})` also creates a `profiles/{uid}` stub without `uid` for a target that has none (e.g. a rating racing `deleteAccount`), which `PublicProfileDto` cannot parse.

**Product/UX:** (a) when a matched guest withdraws, the guests whose requests were denied can never request the reopened meal (decided requests are terminal), so "open for others" excludes the people who already asked; (b) the `match_left` push opens Discover, which never lists the host's own meals and there is no "my meals" screen, so the host cannot see the reopened meal; (c) `LeaveMatchAction` relies on `matchMealProvider`, a one-shot read: after the other person already cancelled, or the meal time passed while the chat stayed open, the action is still shown and the tap fails with the misleading "Check your connection and try again."; (d) restaurant search: no `maxLength` on the field (the callable rejects queries over 80 chars -> generic error), no retry on the error state (offline open of the picker leaves "Something went wrong" until you type), an empty-query Places request is billed every time the picker opens, and the in-memory rate limiter never evicts idle uids; (e) `_pickPhoto` has no try/catch around `ImagePicker().pickImage`, so a platform exception (permission, picker failure) is an uncaught async error reported as fatal (NOT VERIFIED on a device; modern pickers need no permission).

**Analytics:** (a) a brand-new account that relaunches within 2 minutes of signing up fires `signup_completed` twice (the plan accepts only a repeated `signin_completed`); (b) `discovery_viewed` re-fires whenever the viewer's own user/profile doc changes (a rating landing, a profile edit, the public-age self-heal) because the feed provider rebuilds and its `lastIds` guard is per build; (c) `AuthUser.method` takes the last entry of `providerData`, which for an account with several linked providers is not necessarily the one used to sign in; (d) the "every event is fired somewhere" parity test matches `ClassName(` as plain text anywhere in `lib/`, comments included.

**Privacy hygiene:** the Firestore on-disk cache is never cleared on sign-out or after account deletion (no `terminate()` + `clearPersistence()`), so the previous user's private data (own `users` doc with date of birth, chat messages) stays in the app sandbox until the cache is evicted or the app is uninstalled; the privacy policy says deleted data is removed "immediately and permanently" (server side true). On a shared phone, consider clearing persistence on sign-out.

**CI/tooling:** the rules-test job installs and runs `firebase/rules-test/*.test.cjs` but `firebase/functions/test-emulator/` (new, emulator-backed state-machine checks) is not wired into CI; `debugLogDiagnostics: true` is still hard-coded in `routerProvider` (see the 2026-10-09 minor bug, item 7).
